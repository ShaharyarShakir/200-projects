# Spec Delta: agent-execution-loop

## Purpose

Defines the contracts and behavior for structured agent action models, pre-execution safety validation, sandboxed execution in Podman, structured result normalization, and bounded iterative feedback loop orchestration.

## ADDED Requirements

### Requirement: Structured Agent Action Parsing and Protocol
The system SHALL parse and validate structured agent action payloads generated by the LLM agent, supporting discrete actions including `run_command`, `inspect_file`, and `finish`.

#### Scenario: Valid command action parsed
- **WHEN** the agent returns a valid `run_command` action with a command string
- **THEN** the system parses and validates the action into a structured `AgentAction` model

#### Scenario: Valid file inspection action parsed
- **WHEN** the agent returns a valid `inspect_file` action with a target file path
- **THEN** the system parses and validates the action into a structured `AgentAction` model

#### Scenario: Agent completion action parsed
- **WHEN** the agent returns a `finish` action indicating task completion with a summary message
- **THEN** the system parses the completion action and marks the loop ready for termination

### Requirement: Pre-Execution Action Validation and Safety Guardrails
The system SHALL validate all requested actions against strict schema rules and supported action types before any execution occurs. Actions with unsupported action names, malformed schemas, or empty commands SHALL be rejected before execution.

#### Scenario: Unsupported action name rejected
- **WHEN** the agent attempts to execute an unknown or disallowed action type
- **THEN** the system rejects the action, skips sandbox execution, and produces a structured validation error response

#### Scenario: Malformed action payload rejected
- **WHEN** the agent provides an action missing required fields or containing invalid parameters
- **THEN** the system rejects the action and returns an explanatory validation error to the agent

### Requirement: Sandboxed Action Execution
The system SHALL route all approved executable actions strictly through an isolated sandbox container, preventing direct unvalidated host command execution or host file access.

#### Scenario: Command executed in sandbox
- **WHEN** an approved `run_command` action is executed
- **THEN** the system executes the command inside the sandbox container and captures exit code, stdout, stderr, and duration

#### Scenario: File inspected in sandbox
- **WHEN** an approved `inspect_file` action is executed for a file path inside the workspace
- **THEN** the system reads the file content from the sandbox container and returns the text or an error if missing

### Requirement: Iterative Feedback Loop Orchestration
The system SHALL manage the multi-turn conversational loop between the LLM provider and the sandbox, formatting execution results into standardized message structures and feeding them back to the agent for subsequent turns.

#### Scenario: Multi-turn loop execution
- **WHEN** an action execution completes with stdout, stderr, or validation error
- **THEN** the system appends the structured result to the conversation history and invokes the agent provider for the next step

#### Scenario: Agent handles command failure feedback
- **WHEN** a previously executed command fails with a non-zero exit code
- **THEN** the system formats the error and stderr into the feedback message so the agent can adjust its next action

### Requirement: Bounded Loop Termination and Limit Enforcement
The system SHALL enforce deterministic bounds on the execution loop, halting execution when the agent signals completion, when maximum iteration limits are reached, or when error thresholds are exceeded.

#### Scenario: Normal termination on finish action
- **WHEN** the agent emits a valid `finish` action
- **THEN** the loop terminates cleanly with status `COMPLETED` and returns the final run summary

#### Scenario: Max iterations limit reached
- **WHEN** the loop reaches the configured maximum iteration count without the agent finishing
- **THEN** the loop halts execution, sets status to `MAX_ITERATIONS_REACHED`, and returns the accumulated run history

#### Scenario: Consecutive failure threshold reached
- **WHEN** the agent produces consecutive invalid or failed actions exceeding the allowed failure limit
- **THEN** the loop halts execution, sets status to `FAILED`, and records the error details
